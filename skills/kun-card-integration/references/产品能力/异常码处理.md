# 异常码处理（落地必读）

商户对接时必须区分 **三层结果**，再决定：修配置 / 换新单 / 只查单 / 稍后重试。

> 与 [`状态判断与异常处理.md`](状态判断与异常处理.md) 配套：本文专讲 **码值怎么处理**；业务态 `SUCCESS/FAIL/PENDING` 见状态文档。  
> 完整业务子码以开放平台 [`response-code-list`](https://opendocs.kun.global/) / `POST /rest/v2.0/caas/response-code-list` 及接口文档为准；下文为对接处理策略。

---

## 1. 三层模型（先分清再处理）

```text
① HTTP 层          → 连接/超时/4xx/5xx
② 平台/网关层      → 鉴权、限流、公共错误（常见 400xx 或网关体）
③ 业务响应体       → body.code / message + data 内业务状态
```

| 层级 | 看什么 | 成功怎么认 | 失败怎么认 |
|------|--------|------------|------------|
| HTTP | status | 通常 2xx 才解析 body | 超时/无响应/5xx → **未知**，写操作只查单 |
| 平台/网关 | 公共错误码、验签失败文案 | 无网关错误 | `40047` 鉴权等 → **不重试写**，先修密钥/头 |
| 业务 body | `code` + `message` | `code` ∈ `0000` / `0` / `SUCCESS`（以实际为准） | 非成功 → 按下表分类；**即使 code 成功仍要看** `openCardStatus` 等 |

**禁止**：HTTP 200 或 `code=0000` 直接当开卡/充值成功（仍可能 `PENDING`）。

典型成功骨架：

```json
{
  "requestNo": "…",
  "code": "0000",
  "message": "success",
  "data": { "openCardStatus": "PENDING" }
}
```

→ 平台接受成功，业务仍处理中。

---

## 2. 处理动作枚举（代码里用这套）

| 动作代号 | 含义 |
|----------|------|
| `FIX_CONFIG` | 修 App-Key/私钥/Timestamp/白名单等，**禁止**盲重试业务写 |
| `FIX_PARAM_NEW_NO` | 修参数后换 **新** `requestNo` 再写 |
| `IDEMPOTENT_USE_RESULT` | 重复请求：按已有结果更新本地，勿当新失败 |
| `QUERY_ONLY` | 未知/处理中：原 `requestNo` **只查状态**，禁止再开一笔 |
| `RETRY_LATER` | 限流/系统繁忙/请稍后：退避后可重试（写操作优先先查再写） |
| `FAIL_TERMINAL` | 明确业务失败：本地 FAIL，人工或修参后新单 |
| `CONTACT_SUPPORT` | 外部/未知系统错误：保留证据，联系支持 |

---

## 3. 业务响应码 `code`（卡业务常见）

成功：

| code | 含义 | 处理 |
|------|------|------|
| `0000` | 成功 | 继续读 `data` 业务状态 |
| `0` / `SUCCESS` | 部分场景等价成功 | 同上（以联调实际为准） |

常见业务错误码与处理：

| code | 含义（摘要） | 处理动作 | 说明 |
|------|--------------|----------|------|
| `KLC0001` | 失败 | `FAIL_TERMINAL` | 看 `message`；写操作勿原单盲重试 |
| `KLC0002` | 请求参数缺失 | `FIX_PARAM_NEW_NO` | 补必填（如 `secretKey`/`requestNo`/`customerId`） |
| `KLC0003` | 请求参数错误 | `FIX_PARAM_NEW_NO` | 枚举/格式/模式不支持等 |
| `KLC0004` | 请求参数错误（含字段名） | `FIX_PARAM_NEW_NO` | 按 message 中字段修正 |
| `KLC0005` | 系统内部错误，请稍后重试 | `QUERY_ONLY` 或 `RETRY_LATER` | **写操作先查单**；查无再谨慎有限次原单/新单（产品约定） |
| `KLC0006` | 非法请求 | `FIX_CONFIG` / `FIX_PARAM_NEW_NO` | 权限、开关、不合法组合 |
| `KLC0007` | 数据已存在 | `IDEMPOTENT_USE_RESULT` 或 `FIX_PARAM_NEW_NO` | 幂等冲突时取原结果；业务唯一键冲突则换业务键 |
| `KLC0008` | 数据不存在 | `FIX_PARAM_NEW_NO` | ID/产品/持卡人等查无 |
| `KLC0009` | 重复请求 | `IDEMPOTENT_USE_RESULT` | 同 `requestNo` 并发/重放；**不重复执行**，查单或用返回结果 |
| `KLC0010` | 已存在待处理数据 | `QUERY_ONLY` | 有进行中单据，禁止再开同业务 |
| `KLC0011` / `KLC0012` | 加密/解密错误 | `FIX_CONFIG` | 密钥或报文编码问题 |
| `KLC0013` | 外部服务错误，请稍后重试 | `QUERY_ONLY` → `RETRY_LATER` | 写操作先查 |
| `KLC0014` / `KLC0020` | 查询时间跨度超限 | `FIX_PARAM_NEW_NO` | 缩小时间窗（365/31 天） |
| `KLC0015` / `KLC0016` / `KLC0017` | 文件过大/格式不支持/不存在 | `FIX_PARAM_NEW_NO` | 上传与 fileId |
| `KLC0018` | 请一分钟后再试 | `RETRY_LATER` | 退避 ≥60s |
| `KLC0019` | 最大数量为一千 | `FIX_PARAM_NEW_NO` | 批量拆分 |
| `KLC0021` | 共享账户创建数已达上限 | `FAIL_TERMINAL` | 产品/配额，联系商务或复用账户 |
| `KLC9600` | 请求超时 | `QUERY_ONLY` | **禁止**直接再开 |
| `KLC9601` | 请求被拒绝 | `FIX_CONFIG` / `FAIL_TERMINAL` | 结合 message |
| `KLC9999` | 未知错误 | `QUERY_ONLY` + `CONTACT_SUPPORT` | 保留 requestNo/原文 |
| `KLU0001` | 机构不存在 | `FIX_CONFIG` / `FIX_PARAM_NEW_NO` | 核对机构映射 / Customer-No |
| `KLU0002` | 卡产品不存在（文档示例） | `FIX_PARAM_NEW_NO` | 核对 `cardProductCode` / cardBins |
| `KLU0006` | 卡信息不存在（含跨机构） | `FIX_PARAM_NEW_NO` | `updateCardRemark` / 查卡类常见 |
| `KLU0019` | 机构状态非正常 | `FAIL_TERMINAL` / `CONTACT_SUPPORT` | 二级冻结等 |

批量明细里还可能出现 `failCode`（如 `KLC00xx`）：按明细对账，任务头状态见 `状态与枚举.md`（含 `PART_SUCCESS`）。

拉全量说明：

```bash
# 沙箱示例：系统响应码/错误码枚举
python kun_client.py call --env sandbox ... \
  --path /rest/v2.0/caas/response-code-list \
  --body '{"requestNo":"req_codes_001","secretKey":"YOUR_SECRET_KEY"}'
```

（Body 以 OpenAPI 为准；上表策略不随枚举增减而改变。）

## 4. 平台公共错误码（网关/鉴权，新对接也会遇到）

权威页：[平台公共错误码](https://open.kun.global/docs/v2/platform/sdk_guide/error_code/index.html)（以线上为准）。

| 错误码 | 含义 | 处理动作 |
|--------|------|----------|
| `40047` | 鉴权认证失败（验签/密钥/过期等） | `FIX_CONFIG`，**不重试业务写** |
| `40041` / `40042` | 缺少/非法参数（头或协议） | `FIX_PARAM_NEW_NO` 或修请求头 |
| `40044` | 业务处理失败（常带业务子码） | 看子码/`message` → 映射到 §3 或接口文档子码 |
| `40029` | 访问受限（限流/白名单/超时熔断） | IP 白名单：`FIX_CONFIG`；限流：`RETRY_LATER`；熔断：`QUERY_ONLY` |
| `40021` | 授权权限不足 | `FIX_CONFIG` / 联系开通 |
| `40020` | 服务不可用 | `RETRY_LATER`；写操作配合 `QUERY_ONLY` |

旧 YOP 数字码（如 `99001008` 签名无效）仅迁移对照用；**新开放 API 以头签 + body.code 为准**，见 `迁移/鉴权迁移.md`。

## 5. 决策树（写进客户端）

```text
收到响应或异常
├─ 无响应 / 超时 / HTTP 5xx / body 无法解析
│     └─ QUERY_ONLY（原 requestNo）
├─ HTTP 4xx 或平台码 40047 / 签名失败
│     └─ FIX_CONFIG（不重试写）
├─ 平台码 40029 限流 / KLC0018
│     └─ RETRY_LATER（写操作建议先查）
├─ body.code 非成功
│     ├─ KLC0009 / 明确幂等命中 → IDEMPOTENT_USE_RESULT
│     ├─ KLC0002/0003/0004/0008/… 参数类 → FIX_PARAM_NEW_NO
│     ├─ KLC0005/0013/9600/9999 → QUERY_ONLY（± CONTACT_SUPPORT）
│     └─ 其他明确失败 → FAIL_TERMINAL
└─ body.code 成功
      └─ 读业务状态 SUCCESS / FAIL / PENDING → 见状态判断文档
```

## 6. Agent / 代码交付强制项

生成可落地代码时必须：

1. 解析并分支 **HTTP**、**平台码**（若有）、**`body.code`**、**业务状态** 四层（至少 HTTP + code + 业务态）。  
2. 对 `KLC0009` / 重复 `requestNo` 走幂等，不双花。  
3. 对超时、`KLC9600`、`KLC0005`、`KLC0013`、5xx：**只查不重开**。  
4. 日志记录 `requestNo` + `code` + `message`（脱敏）；禁止只打 HTTP 200。  
5. 迁移客户：说明旧 YOP 公共码与新 `body.code` 的对应处理，避免混用两套客户端判码逻辑。

缺以上项 → 不得声称可上生产。
