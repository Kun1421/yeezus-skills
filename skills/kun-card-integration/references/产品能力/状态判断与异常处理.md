# 状态判断与异常处理（落地必读）

商户系统对接时，**正确判态 + 可恢复的异常处理**比「发出请求」更重要。本章是 Agent 生成落地代码时的强制规范。

---

## 1. 两层结果模型（先分清）

每次调用都要分开判断：

| 层级 | 看什么 | 含义 |
|------|--------|------|
| **传输/平台层** | HTTP 状态、响应头验签、响应体 `code`/`message` | 请求是否被平台接受、签名是否正确 |
| **业务层** | `data` 内状态字段（如 `openCardStatus`、充值状态、KYC 状态） | 业务是否成功/失败/处理中 |

**禁止**：仅凭 HTTP 200 或前端展示成功，就更新本地终态。  
**禁止**：把平台 `code` 成功当成开卡/充值已成功（仍可能 `PENDING`）。

典型成功响应骨架：

```json
{
  "requestNo": "…",
  "code": "0000",
  "message": "success",
  "data": { "openCardStatus": "PENDING", "orderId": "…" }
}
```

此处：平台接受成功，但业务仍在处理 → 本地记「处理中」，进入轮询/等通知。

## 2. 业务状态判定矩阵

### 2.1 开卡 / 销卡 / 卡充值 / 卡转出

| 状态 | 本地应如何处理 | 可否换同 requestNo 重试写操作 |
|------|----------------|------------------------------|
| SUCCESS | 更新终态成功；落卡号/订单号等 | 否（已成功） |
| FAIL | 更新终态失败；记录 message；可**新** requestNo 重试 | 否（同单勿盲重试） |
| PENDING | 保持处理中；启动查询补偿 | 否；只查状态 |

批量任务额外：`PROCESSING`/`PENDING` 继续查任务；`PART_SUCCESS` 按明细对账；`FAIL`/`SUCCESS` 终态。

### 2.2 共享账户充值 / 转出

| 状态 | 处理 |
|------|------|
| SUCCESS / FAIL | 终态 |
| PROCESSING | 处理中（等同开卡场景的 PENDING）→ 继续查询 |

### 2.3 卡状态（查询）

| 状态 | 业务含义 | 常见限制 |
|------|----------|----------|
| NORMAL | 正常 | 仍须看激活态 |
| FREEZE | 冻结 | 通常不可交易 |
| CANCELLING | 销卡中 | 禁止充值/改配 |
| CANCEL | 已注销 | 禁止资金与配置 |
| LOCK | 锁定（常伴封锁码） | 先处理封锁码/客服 |

激活态：`ACTIVATED` / `UNACTIVATED`。

### 2.4 KYC（消费卡）

| 类型 | 取值 | 下一步 |
|------|------|--------|
| 申请数字态 | 0 认证中 | 等通知或查询 |
| | 1 成功 | 可开卡 |
| | 2 失败 | 按原因补件/重报（新 requestNo） |
| 案件态 | PENDING / SUPPLEMENT | 等待或补资料 |
| | APPROVED | 可开卡 |
| | REJECTED | 终止或按产品重报 |

**未 APPROVED / 未认证成功，禁止开卡。**

### 2.5 交易查询

| 状态 | 处理 |
|------|------|
| SUCCESS | 成功 |
| FAILED | 失败（拼写是 FAILED） |
| PENDING | 处理中 |

### 2.6 授权 Webhook（同步）

商户必须在超时前返回：

| authResult | 含义 |
|------------|------|
| A | 批准 |
| D | 拒绝 |

同一 `transactionId` 重复投递 → **返回与首次一致**的决策（幂等）。

## 3. 终态确认：查询 + 通知双通道

```text
写操作（开卡/充值/转出/销卡…）
    ├─ 同步返回 SUCCESS/FAIL → 可初判，仍建议落库并对账
    ├─ 同步返回 PENDING / 超时 / 未知 → 必须查单
    └─ 若已配置结果类 Webhook → 通知与查单互相校验，以一致终态为准
```

**落地规则：**

1. 发起写操作前生成本地业务单，绑定唯一 `requestNo`。  
2. 同步结果写入本地；非终态进入「待确认」。  
3. 定时任务按指数退避查询（如 2s → 5s → 15s → 30s，上限次数/时长可配）。  
4. Webhook 到达时：验签 → 幂等键去重 → 仅允许「处理中 → 终态」或同终态覆盖；**禁止终态回退**。  
5. 通知与查询冲突：以再次查询为准，并告警人工。

## 4. 异常分类与处理策略

> **具体错误码（`0000` / `KLC*` / 平台 `400xx`）的处理动作表**见专章 [`异常码处理.md`](异常码处理.md)。本节是分类策略；码值以专章为准。

### 4.1 签名 / 鉴权类

现象：验签失败、非法应用、时间戳超窗等。

| 动作 | 说明 |
|------|------|
| 不重试业务写 | 先修配置 |
| 检查项 | App-Key、Customer-No、私钥、Timestamp 毫秒、待签字段是否含 body 顶级字段 + customerNo + timestamp、key 小写排序、未把 Sign 加入待签 |

### 4.2 参数 / 业务拒绝类（明确 FAIL 或参数错误码）

| 动作 | 说明 |
|------|------|
| 不自动原单重试 | 修参数后用**新 requestNo** |
| 典型 | 产品码错误、KYC 未过、实体卡缺邮寄字段、accountMode 不支持 |

### 4.3 超时 / 连接失败 / HTTP 5xx / 响应无法解析

| 动作 | 说明 |
|------|------|
| **视为未知** | 本地保持处理中 |
| 下一步 | 用原 `requestNo` **只查状态**，禁止直接再开一笔 |
| 查无单 | 按产品约定：可有限次用原 requestNo 重试写，或人工；默认「先查后写」 |

### 4.4 幂等冲突（重复 requestNo）

返回已存在结果则按原结果更新本地；不要当新失败。

### 4.5 Webhook 异常

| 现象 | 处理 |
|------|------|
| 验签失败 | 拒绝（4xx），打安全日志；不改业务态 |
| 处理超时 | 授权场景可能导致平台按约定默认拒绝/批准——须在联调确认；商户侧应降超时依赖 |
| 重复通知 | 幂等成功应答 |
| 收不到 | 查单补偿 + 检查公网 URL/密钥配置 |

## 5. 推荐状态机（商户本地）

以开卡为例（充值/转出同构）：

```text
CREATED ──调用成功──► ACCEPTING
    │                    │
    │ 明确 FAIL          ├─ SUCCESS ──► SUCCESS
    └──────────────────► FAIL         ├─ FAIL ────► FAIL
                                      └─ PENDING ─►（轮询/通知）─┘
超时/未知 ──► UNKNOWN ──只查单──► 同上终态
```

代码中用枚举，避免散落字符串比较；映射平台状态见 `状态与枚举.md`。

## 6. Agent 生成落地代码时的强制清单

输出实现代码必须包含：

1. **唯一 requestNo** 生成策略（如 `bizPrefix + snowflake/uuid`）  
2. **平台层校验**：HTTP、（建议）响应验签、`code`  
3. **业务层判态**：SUCCESS / FAIL / PENDING（或 PROCESSING）分支  
4. **查单补偿**方法（可先给伪代码 + 定时入口）  
5. **幂等**：DB 唯一约束或分布式锁（按 requestNo / transactionId）  
6. **敏感字段**：卡号/CVV/证件不落明文日志  
7. **异常**：区分可重试（未知）与不可重试（明确失败）  
8. **Webhook**（若场景需要）：验签、A/D、幂等、快速返回  

缺以上任一项，不得声称「可直接上生产」；可标「沙箱可跑通，上生产前补齐补偿与幂等」。
