# 鉴权认证机制（摘要）

来源：[opendocs — 鉴权认证机制](https://opendocs.kun.global/docs/api-integration/authentication-and-authorization-mechanism)

## 概述

所有对 KUN-API 的请求都必须进行 **RSA（SHA256withRSA）** 签名。请求头中的 `Customer-No` 与 `Timestamp` **必须参与签名**。

## Header → Signature 映射

- Header 中只有 `Customer-No`、`Timestamp` 参与签名。
- 转换：`Customer-No` → `customerNo`，`Timestamp` → `timestamp`。
- 业务参数（query / form / JSON body **顶级字段**）同样参与签名。
- **不要**把 `Sign` 本身加入待签内容。

## 算法与编码

| 项 | 值 |
|----|-----|
| 算法 | SHA256withRSA |
| 密钥 | RSA2048 |
| 签名输出 | Base64 |
| 字符集 | UTF-8 |
| 时间窗 | 与服务器误差建议 ≤ 5 分钟（防重放） |

## 请求签名步骤

1. 收集字段：全部业务顶级参数 + `customerNo` + `timestamp`。
2. 规范化：参数名驼峰；参与排序前 **key 转小写**；`null` 视为 `""`（建议不放入 null key）。
3. 按 key ASCII 升序排序，拼成 `k1=v1&k2=v2&...`。
4. UTF-8 字节用商户**私钥** SHA256withRSA，结果 Base64 放入请求头 `Sign`。

请求头示例：

```text
App-Key: APP_0000001
Api-Version: 2
Customer-No: 10037227
Timestamp: 1758012303512
Sign: <Base64-Signature>
```

## 响应验签

1. 取响应中的 `sign`、`timestamp` 及待验数据（通常只取报文 `data`）。
2. 按与请求相同规范构造待验签字符串。
3. 用 KUN **公钥** SHA256withRSA 验签；校验时间窗。

## 常见注意事项

- key 大小写不一致会导致验签失败 → 统一小写排序。
- 漏签 `customerNo`/`timestamp`，或误签 `Sign` 自身。
- 时间戳超窗或重放。
- 私钥泄露风险；生产建议 HSM/KMS。

> 卡业务 body 中的 `secretKey` 是**机构业务密钥**，与 RSA 签名私钥不同，二者都需要但职责不同。
